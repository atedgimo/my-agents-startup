## 🏛️ System Architecture\n\n*Goal: Define the blueprint for the Offline Habit Tracker.* \n---\n\n### I. Core Principles & Constraints\n\n1. **Zero-Cost Mandate:** Everything must be free and open source.\n2. **Data Sovereignty:** All data is stored locally in an SQLite file on the user's device.\n3. **Client-Server Model:** FastAPI acts as a local API service, mediating all interactions between the React Frontend and the SQLite Database.\n\n### II. Data Model (SQLite Schema)\n\nThe data model defines three core entities:\n\n**1. Users Table (Minimal)**\n*   `user_id`: INTEGER PRIMARY KEY AUTOINCREMENT\n*   `username`: TEXT UNIQUE NOT NULL\n*   `created_at`: TIMESTAMP DEFAULT CURRENT_TIMESTAMP\n\n**2. Habits Table**\n*   `habit_id`: INTEGER PRIMARY KEY AUTOINCREMENT\n*   `user_id`: INTEGER FOREIGN KEY (References Users)\n*   `name`: TEXT NOT NULL (e.g., 'Drink 8 glasses of water')\n*   `description`: TEXT\n*   `frequency`: TEXT (e.g., 'Daily', 'Weekdays')\n*   `created_at`: TIMESTAMP DEFAULT CURRENT_TIMESTAMP\n\n**3. DailyEntries Table**\n*   `entry_id`: INTEGER PRIMARY KEY AUTOINCREMENT\n*   `habit_id`: INTEGER FOREIGN KEY (References Habits)\n*   `date`: DATE NOT NULL (YYYY-MM-DD format for easy querying of streaks)\n*   `completed`: BOOLEAN NOT NULL (1 for completed, 0 otherwise)\n*   `notes`: TEXT (Optional context or reflections for the day)\n\n---\n\n### III. API Specification (FastAPI Endpoints)\n\nThese endpoints define the service contract between the Frontend Client and the Backend API.\n\n#### **A. Habit Management (`/api/v1/habits`)**\n\n*   `POST /`: Creates a new habit. Body: `{name, description, frequency}`.\n    *   Response: New `habit_id`.\n*   `GET /`: Retrieves all habits for the current user.\n    *   Response: List of Habits objects.\n*   `PUT /{habit_id}`: Updates an existing habit's metadata.\n    *   Body: `{name?, description?, frequency?}`.\n\n#### **B. Daily Entry Management (`/api/v1/entries`)**\n\n*   `GET /?date={YYYY-MM-DD}&habit_id={id}`: Retrieves the completion status for a specific habit on a given day.\n    *   Query Params: `date`, optional `habit_id`.\n    *   Response: `{completion_status: boolean, notes: string}`.\n*   `POST /`: Records or updates an entry (completes/misses a habit).\n    *   Body: `{date: YYYY-MM-DD, habit_id: int, completed: bool?, notes?: string}`.\n    *   Response: Success status and the saved `entry_id`.\n\n#### **C. User & Status (`/api/v1/status`)**\n\n*   `GET /`: Retrieves high-level metrics (e.g., total active habits, current streak count) for dashboard display.\n    *   Response: `{total_habits: int, longest_streak: {habit_id: int, count: int}, recent_activity: list}`\n\n---\n\n### IV. LLM Integration (Async Feature)\n\nThe local LLM endpoints will live under a separate `/api/v1/llm` prefix and should be rate-limited to prevent resource exhaustion on the user's machine.\n*   Example: `POST /api/v1/llm/analyze`: Endpoint for submitting raw text (e.g., a journal entry) for local analysis (sentiment, summarization).\n\n---"
